# RAG のコンテキストを検索で当たった箇所から組み立てる

## 目的

RAG 質問応答で、検索が当たった箇所を LLM へ渡す。ファイルの後半にある知識にも
答えられるようにする。

## 目標

- ベクトル検索で当たったチャンクの本文を、LLM へ渡すコンテキストに使う
- 全文検索だけで当たったファイルでは、一致箇所の周辺をコンテキストに使う
- RRF（2 つの検索の順位を合算する手法）で、同じファイルを重複して数えない
- プロンプトへ載せる本文の上限を今と同じに保つ（5 ファイル × 1000 文字）

## 非目標

- チャンクの長さ（500 文字）・重なり（100 文字）の変更
- モデルの `context_length` に応じたコンテキスト量の調整
- 再ランキング（reranker）の導入
- 同じファイルの隣り合うチャンクの結合（重なりの 100 文字は重複したまま渡す）
- システムメッセージ・プロンプトの文言の変更
- 検索モードの UI の変更
- 検索精度・回答精度のベンチマーク（`docs/TODO.md`「品質ベンチマーク」の範囲）

## 問題

2026-11-20 に `src-tauri/src/commands/mod.rs` の `chat` を読んで確かめた事実:

- ハイブリッド検索の結果からファイルパスだけを取り出し、RRF で上位 5 ファイルを選ぶ
- 選んだファイルをディスクから読み直し、先頭 1000 文字だけを渡す（1052〜1060 行）
- `VectorSearchResult` はチャンクの本文 `text` を持つが、`chat` は使わずに捨てている
- `reciprocal_rank_fusion`（`domain/search/hybrid.rs`）はパスの重複を除かない。
  ベクトル検索の結果はチャンク単位なので、1 つのファイルから複数のチャンクが入ると、
  そのファイルのスコアが重ねて加算される。検索モードの `hybrid_search` も同じ関数を使う
- `docs/architecture.md`「2.1 RAGパイプライン」も「各ファイルの先頭1000文字」と
  書いており、実装は設計どおりである

ここからの推論（実測していない）:

- 答えが 1000 文字目より後ろにあるファイルは、検索で当たっても LLM に答えが見えない。
  システムメッセージの指示により「情報が見つかりませんでした」と答える経路ができる
- 埋め込みモデルが無くベクトル検索が使えないとき（全文検索へのフォールバック）は、
  全ファイルが同じ問題を持つ

## 概要設計

### コンテキストの選び方

1. 全文検索で上位 5 ファイル、ベクトル検索で上位 20 チャンクを引く。チャンクを 20 に
   増やすのは、5 ファイル × 2 チャンクを埋められるようにするためである
2. RRF でファイルの順位を決め、上位 5 ファイルを選ぶ
3. ファイルごとに本文を決める

| そのファイルの当たり方 | コンテキストに入れる本文 |
|---|---|
| ベクトル検索で当たった | 当たったチャンクを順位の高い順に最大 2 つ選び、`chunk_index` の順に並べる |
| 全文検索だけで当たった | ファイルを読み、一致箇所（スニペットの断片）を中心に 1000 文字の窓を切る |
| 一致箇所が見つからない | 今と同じく先頭 1000 文字 |

- 同じファイルの 2 つのチャンクは 1 つの `ContextChunk` にまとめ、区切りの行（`…`）で
  つなぐ。プロンプトの組み立て（`build_rag_prompt`）と参照元の一覧は 1 ファイル 1 件のまま
  変わらない
- ベクトル検索のチャンクはインデックス作成時の本文なので、ディスクを読み直さない。
  全文検索だけで当たったファイルと、一致箇所の探索に限ってディスクを読む

### 変更の一覧

| 箇所 | 変更 | 振る舞い |
|---|---|---|
| `domain/search/hybrid.rs` `reciprocal_rank_fusion` | 各リストでパスの初出だけを数える | 検索モードの順位も変わる（重複加算を除く） |
| `domain/embedding` `VectorSearchResult` | `chunk_index` を足す | 追加のみ |
| `infra/hnsw` `search_nearest` | `ChunkMeta.chunk_index` を写す | 追加のみ |
| `domain/search` `SearchResult` | プレーンテキストの断片 `fragment` を足す。`#[serde(skip_serializing)]` で IPC へは出さない | IPC の形は変わらない |
| `infra/tantivy` `search` | `Snippet::fragment()` を `fragment` へ入れる | 追加のみ |
| `domain/llm/rag.rs` | コンテキストを選ぶ純粋関数を足す。ファイルの読み込みは関数を引数で受ける | 新規 |
| `commands/mod.rs` `chat` | 入力を集めて上の関数を呼ぶだけにする。ベクトル検索の件数を 5 → 20 | RAG のコンテキストが変わる |

- スニペットの断片は `to_html()` でなく `fragment()` から取る。`to_html()` は `&` や
  `<` をエスケープするので、ファイルの本文の中で見つからなくなる。tantivy 0.25.0 の
  `src/snippet/mod.rs` に `pub fn fragment(&self) -> &str` があることを確かめた
- RRF の重複除去を `chat` の側でなく関数の側で行うのは、同じ概念の規則を 2 か所に
  割らないためである。検索モードの順位も変わるので、裁定を仰ぐ（裁定点 2）

### 裁定を仰ぐ点

1. **全文検索だけで当たったファイルの本文**
   - 推奨: 一致箇所を中心とする窓。ベクトル検索が使えないフォールバックのときは
     全ファイルがこの経路を通るので、先頭のままでは改善が届かない
   - 代案: 今と同じ先頭 1000 文字。変更は小さいが、フォールバックの時には何も改善しない
2. **RRF の重複除去の範囲**
   - 推奨: `reciprocal_rank_fusion` の中で除く。RRF は文書ごとに各リストで 1 回だけ数える
     定義であり、検索モードの重複加算も同じ欠陥である
   - 代案: `chat` の側でだけ除く。検索モードの順位は変わらないが、同じ関数の使い方が
     2 通りに割れる
3. **CP6 第三者視点レビュー**: 実施を提案する（到達基準の最終項）
