# RAG のコンテキストを検索で当たった箇所から組み立てる

## 目的

RAG 質問応答で、検索が当たった箇所を LLM へ渡す。ファイルの後半にある知識にも
答えられるようにする。

## 目標

- ベクトル検索で当たったチャンクの本文を、LLM へ渡すコンテキストに使う（FR-030）
- 全文検索だけで当たったファイルでは、一致箇所の周辺をコンテキストに使う（FR-030）
- RRF（2 つの検索の順位を合算する手法）で、同じファイルを重複して数えない（FR-022）
- プロンプトへ載せる本文の上限を今と同じに保つ（5 ファイル × 1000 文字）（FR-030）
- CP6 の裁定で加えた目標:
  - コンテキストは今の本文から選び、インデックス作成後に消した・書き換えたファイルの
    古い本文を渡さない（FR-030・FR-034）
  - 両方の検索で当たったファイルでも、全文検索の一致箇所をコンテキストに届ける（FR-030）
  - RRF の同点の並びを実行ごとに変えない（FR-022）
  - 検索結果一覧で、ベクトル検索由来のスニペットを HTML として実行させない（FR-022）
  - フォルダを切り替えたら、前のフォルダの索引を検索とチャットに使わない（FR-022・FR-030）

## 非目標

- チャンクの長さ（500 文字）・重なり（100 文字）の変更
- モデルの `context_length` に応じたコンテキスト量の調整
- 再ランキング（reranker）の導入
- 同じファイルの隣り合うチャンクの結合（重なりの 100 文字は重複したまま渡す）
- システムメッセージ・プロンプトの文言の変更
- 検索モードの UI の変更
- 検索精度・回答精度のベンチマーク（`docs/TODO.md`「品質ベンチマーク」の範囲）
- インデックス鮮度の根本の対処（開くときの差分同期・更新の再試行。残課題へ起票）
- フロントエンドへ渡す形（`SearchResult`・`HybridSearchResult` のキー）の変更（不変条件）

## 問題

2026-11-20 に `src-tauri/src/commands/mod.rs` の `chat` を読んで確かめた事実:

- ハイブリッド検索の結果からファイルパスだけを取り出し、RRF で上位 5 ファイルを選ぶ
- 選んだファイルをディスクから読み直し、先頭 1000 文字だけを渡す（1052〜1060 行）
- `VectorSearchResult` はチャンクの本文 `text` を持つが、`chat` は使わずに捨てている
- `reciprocal_rank_fusion`（`domain/search/hybrid.rs`）はパスの重複を除かない。
  ベクトル検索の結果はチャンク単位なので、1 つのファイルから複数のチャンクが入ると、
  そのファイルのスコアが重ねて加算される。検索モードの `hybrid_search` も同じ関数を使う
- `docs/architecture.md`「2.1 RAGパイプライン」も「各ファイルの先頭1000文字」と
  書いており、実装は設計どおりである

ここからの推論（実測していない）:

- 答えが 1000 文字目より後ろにあるファイルは、検索で当たっても LLM に答えが見えない。
  システムメッセージの指示により「情報が見つかりませんでした」と答える経路ができる
- 埋め込みモデルが無くベクトル検索が使えないとき（全文検索へのフォールバック）は、
  全ファイルが同じ問題を持つ

## 概要設計

### コンテキストの選び方

1. 全文検索で上位 5 ファイル、ベクトル検索で上位 20 チャンクを引く。件数は
   `ContextLimits` から導く。ベクトル検索は 5 ファイル × 2 チャンクをちょうど埋める件数の
   2 倍を引く（結果が少数のファイルへ偏り、今の本文に残らないチャンクも除くため）
2. RRF でファイルの順位を決め、上から読めるファイルを 5 つ選ぶ。読めないファイル
   （インデックス作成後に消えた等）は除いて次の順位で補う
3. ファイルごとに、ディスクから読み直した今の本文から選ぶ

| そのファイルの当たり方 | コンテキストに入れる本文 |
|---|---|
| ベクトル検索で当たったチャンクが今の本文に残る | 順位の高い順に最大 2 つ（同じ本文は 1 つと数える）。全文検索の一致箇所がどれにも含まれなければ、2 つ目を一致箇所を中心とする 500 文字の窓に替える |
| 残るチャンクが無い（全文検索だけで当たった・書き換えた） | 一致箇所（スニペットの断片）を中心に 1000 文字の窓を切る |
| 一致箇所が見つからない | 今と同じく先頭 1000 文字 |

- 選んだ部分は今の本文での位置の順に並べ、1 つの `ContextChunk` にまとめて区切りの行
  （`…`）でつなぐ。プロンプトの組み立て（`build_rag_prompt`）と参照元の一覧は 1 ファイル
  1 件のまま変わらない
- ベクトル検索のチャンクはインデックス作成時の本文なので、そのまま使うと消した・
  書き換えたファイルの古い本文が渡る。チャンクは今の本文に含まれるときだけ使う

### 変更の一覧

| 箇所 | 変更 | 振る舞い |
|---|---|---|
| `domain/search/hybrid.rs` `reciprocal_rank_fusion` | 各リストでパスの初出だけを数える。同点はパスの順 | 検索モードの順位も変わる（重複加算を除く） |
| `domain/search/hybrid.rs` `RRF_K`・`display_snippet` | k を共有の定数にする。スニペットの選び方を切り出し、チャンクテキストを HTML エスケープする | ベクトル由来のスニペットがエスケープされる |
| `domain/embedding` `VectorSearchResult`・`VectorSearcher` | `chunk_id` の説明を直し、距離の昇順を契約として書く | なし |
| `domain/search` `SearchResult` | プレーンテキストの断片 `fragment` を足す。`#[serde(skip_serializing)]` で IPC へは出さない | IPC の形は変わらない |
| `infra/tantivy` `search` | `Snippet::fragment()` を `fragment` へ入れる | 追加のみ |
| `domain/llm/rag.rs` | コンテキストを選ぶ純粋関数と `ContextLimits` を足す。ファイルの読み込みは関数を引数で受ける | 新規 |
| `commands/mod.rs` `chat` | 入力を集めて上の関数を呼ぶ。検索件数は `ContextLimits` から（ベクトル 5 → 20）。読めないファイルと全文検索の失敗をログへ残す | RAG のコンテキストが変わる |
| `commands/mod.rs` `build_index`・`open_indexed_folder` | 前のフォルダの索引を解放してから作る・読む | フォルダ切替の後に前の索引を使わない |

- スニペットの断片は `to_html()` でなく `fragment()` から取る。`to_html()` は `&` や
  `<` をエスケープするので、ファイルの本文の中で見つからなくなる。tantivy 0.25.0 の
  `src/snippet/mod.rs` に `pub fn fragment(&self) -> &str` があることを確かめた
- RRF の重複除去を `chat` の側でなく関数の側で行うのは、同じ概念の規則を 2 か所に
  割らないためである。検索モードの順位も変わるので、裁定を仰ぐ（裁定点 2）

### 裁定を仰ぐ点

1. **全文検索だけで当たったファイルの本文**
   - 推奨: 一致箇所を中心とする窓。ベクトル検索が使えないフォールバックのときは
     全ファイルがこの経路を通るので、先頭のままでは改善が届かない
   - 代案: 今と同じ先頭 1000 文字。変更は小さいが、フォールバックの時には何も改善しない
2. **RRF の重複除去の範囲**
   - 推奨: `reciprocal_rank_fusion` の中で除く。RRF は文書ごとに各リストで 1 回だけ数える
     定義であり、検索モードの重複加算も同じ欠陥である
   - 代案: `chat` の側でだけ除く。検索モードの順位は変わらないが、同じ関数の使い方が
     2 通りに割れる
3. **CP6 第三者視点レビュー**: 実施を提案する（到達基準の最終項）
